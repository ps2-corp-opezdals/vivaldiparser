> ⚠️ **Перед стартом** вся команда должна понимать: работа сдаётся **как модули к каркасу** (`Modules/<Имя>/Parser.py`), а не «просто библиотекой». Согласовать с руководителем (делает лидер, ПВ-1).

> ℹ️ **Что уже готово и что делаем сами.** Каркас, обвязка (`Interfaces/`, `Common/`), примеры модулей (`DrWebAlerts`, `CompatibilityAssistant`, `MuiCache`) — готовы, их не трогаем. **Нет** модулей под Vivaldi и **нет** данных из реального профиля Vivaldi (в `Source/` лежат только логи Dr.Web) — это и есть наша работа. ## Общие правила для всех модулей (контракт команды)

Обязательны для ПВ-2 … ПВ-6. Нарушение контракта = тест ПВ-7 упадёт.

1. **Расположение:** создаётся папка `Modules/<ИмяМодуля>/Parser.py`.
2. **Класс:** внутри файла обязательно `class Parser` c `def __init__(self, parameters: dict)` и `async def Start(self) -> dict`.
3. **Возврат:** `Start()` возвращает `{MODULENAME: outputWriter.GetDBName()}`.
4. **Пути:** имя файла-артефакта указывается жёстко, папка — только через `STORAGE` (параметр каркаса). Полные пути на своём ПК не хардкодить.
5. **Отсутствующий файл:** если артефакта нет — тихо `return {}`, не падать.
6. **Время:** пересчёт Chromium-времени выполняется ТОЛЬКО через общий модуль `chrome_time.py` (его делает ПВ-1).
7. **Поля БД:** единый набор полей на группу: `DateTime_UTC`, `Timestamp_UTC`, `DateTime_Local`, `TimeZoneOffset`, `DataSource` + специфичные для артефакта.
8. **Docstring'и:** у каждого метода docstring на русском (формат как в `Modules/DrWebAlerts/Parser.py`).
9. **Git:** у каждого своя ветка; коммиты после логически завершённого куска; слияние только через ревью (лидер / QA).
10. **Не ломать чужое:** модули независимы — не редактировать файлы каркаса (`Interfaces/`, `Common/`, `Run.py`) и чужие папки модулей.
11. **Стартовая точка каждого модуля:** скопировать структуру `Modules/DrWebAlerts/Parser.py` и переписать логику под свой артефакт.

# ПВ-1. Окружение, данные Vivaldi, лидерство

**Цель:** подготовить окружение, добыть **реальные данные из профиля Vivaldi** (их нет в проекте) и обеспечить управление проектом.

**Делает:** Лидер / архитектор.

**Зависимости:** нет (стартует первым).

### Что сделать

1. **Git.** Создать репозиторий (GitHub/GitLab), пригласить команду; ветки: `main`, `develop`, `feature/<имя>`; проверить `.gitignore` (`.venv/` не должен попадать в git); договориться о формате коммитов (кратко, на русском).
2. **Окружение.** `python3 -m venv .venv`, `pip install -r requirements.txt`; убедиться, что `python Run.py --source_folder Source --output_name result.sqlite` запускается с готовыми примерами. Если Python 3.14 тянет библиотеки — ок, иначе установить Python 3.12 (`brew install python@3.12`) и работать на нём.
3. **Данные Vivaldi (главное!)** — их нужно добыть:
   - На отдельной ВМ/системе установить Vivaldi.
   - «Нажить» артефакты: походить по сайтам (история), добавить закладки, скачать файлы (загрузки), дать накопиться куки и кешу.
   - Скопировать папку профиля `Default/` в проект: `SourceVivaldi/Default/` (внутри `History`, `Cookies`/`Network/Cookies`, `Bookmarks`, `Cache/...`). Не класть в `Source/` (там Dr.Web — не мешать примеру).
   - Если нет машины/ВМ под Vivaldi — попросить у руководителя готовый выгруженный профиль.
   - Убедиться, что скопированный профиль НЕ открыт живым браузером (файлы залочены / есть WAL).
4. **Общий модуль времени `chrome_time.py`.** Написать один раз для всех:
   - `chromium_to_filetime(microseconds) -> int` (умножить на 10);
   - `chromium_to_datetime(microseconds, tz) -> datetime` (через `TimeConverter.FILETIMEToDatetime`);
   - `format_datetime(dt) -> str` в едином формате.
5. **Связь с руководителем.** Уточнить и зафиксировать в `QUESTIONS.md`: ОС (Windows/macOS/обе); расшифровывать ли куки; подтверждение формата сдачи (модули к каркасу); требования к отчёту.
6. **Интеграция.** После сдачи модулей: собрать всё, запустить на `SourceVivaldi`, проверить, что каждый модуль создал свою БД, написать `README.md` по запуску.

### Выход

- Репозиторий с ветками.
- Работающее окружение + инструкция по запуску.
- Папка `SourceVivaldi/` с реальными данными Vivaldi.
- `chrome_time.py`.
- `QUESTIONS.md` с ответами руководителя.

### Критерии приёмки

- Любой участник клонирует репозиторий и по инструкции запускает каркас.
- Есть данные Vivaldi для проверки модулей.
- Ответы руководителя зафиксированы письменно.

# ПВ-2. Модуль `VivaldiHistory` (история посещений)

**Цель:** вытащить из базы `History` историю посещений (таблицы `urls` и `visits`) и записать её в свою БД каркаса.

**Делает:** Разработчик (история).

**Зависимости:** ПВ-1 (окружение, данные, `chrome_time.py`).

### Что сделать

1. Изучить схему `History` (SQLite):
   - `urls` → `id`, `url`, `title`, `visit_count`, `last_visit_time` (Chromium-время);
   - `visits` → `id`, `url`, `visit_time`, `from_visit`, `transition`, `visit_duration` (мс).
2. Читать базу через готовый `SQLiteDatabaseInterfaceReader` из `Common/Routines.py` (режим только чтения) или `sqlite3` напрямую по копии файла.
3. Формировать записи: url, заголовок, число визитов; на каждый визит — время (через `chrome_time.py`) и тип перехода.
4. Перевести `transition` в человекочитаемое имя (0=Link, 1=Typed, 2=AutoBookmark; при необходимости битовая расшифровка).
5. Поля БД: `URL`, `Title`, `VisitCount`, `DateTime_UTC`, `Timestamp_UTC`, `DateTime_Local`, `TimeZoneOffset`, `Transition`, `TransitionName`, `VisitDuration`, `DataSource`.
6. Учесть WAL-файлы: если рядом с `History` есть `History-wal`/`History-shm` — читать копию вместе с ними или предупредить в логе.

### Выход

- Папка `Modules/VivaldiHistory/Parser.py`.
- БД `VivaldiHistory_result.sqlite` с записями посещений (время корректно в UTC и локальном).

### Критерии приёмки

- Есть записи с правильным пересчётом времени (сверить одну дату вручную).
- При отсутствии файла `History` — тихий выход.
- Проходит тесты ПВ-7.

# ПВ-3. Модуль `VivaldiDownloads` (загрузки)

**Зависимости:** ПВ-1.

   - `downloads_url_chains` → `id`, `chain_index`, `url`.
2. На каждую загрузку: URL (из chain), целевой и текущий путь, время начала/конца (через `chrome_time.py`), принятые/полные байты, состояние.

4. Поля БД: `URL`, `TargetPath`, `CurrentPath`, `DateTimeStart_UTC`, `TimestampStart_UTC`, `DateTimeEnd_UTC`, `TimestampEnd_UTC`, `ReceivedBytes`, `TotalBytes`, `State`, `DangerType`, `InterruptReason`, `DataSource`.

### Выход

- Папка `Modules/VivaldiDownloads/Parser.py`.
- БД `VivaldiDownloads_result.sqlite`.

### Критерии приёмки

- Каждая реальная загрузка из данных Vivaldi отражена записью с корректными URL и байтами.
- Время начала/конца согласуется с `History`.

# ПВ-6. Модуль `VivaldiCache` (кеш)

**Цель:** извлечь сведения о записях кеша браузера (какие URL сохранены) из каталога `Cache/Cache_Data`.

**Делает:** Разработчик (кеш).

**Зависимости:** ПВ-1.

### Что сделать

1. Изучить формат **Simple Cache** Chromium:
   - каталог `Cache/Cache_Data/`: файлы `index`, `f_XXXXXX` (данные), `index-directory`;
   - запись начинается с магического числа `0xFCFB6D1B`, затем ключ (URL ресурса) и потоки данных;
   - описание — по запросу «chromium simple cache f_ files format».
2. Написать чтение: пройти по файлам `f_*`, прочитать заголовок, извлечь URL-ключ, размер, время создания; содержимое — опционально BLOB.
3. Битые/частичные записи пропускать с предупреждением в лог (не ронять модуль).
4. Поля БД: `URL (Key)`, `FileName`, `DateTimeCreate_UTC`, `TimestampCreate_UTC`, `Size`, `Content` (BLOB, опционально), `DataSource`.

### Выход

- Папка `Modules/VivaldiCache/Parser.py`.
- БД `VivaldiCache_result.sqlite`.

### Критерии приёмки

- Обработано ≥50% записей из реального кеша (для остальных не читается ключ — это допустимо).
- Модуль не падает на повреждённых записях.
- Проходит тесты ПВ-7.
